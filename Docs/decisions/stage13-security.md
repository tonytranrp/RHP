# Stage 13: security for every deployment

**Status:** 13a (hardening, sandbox and network fixes, dev sessions) and 13b (identities, certificates, root of trust, scopes, wire revision 7) are implemented and tagged `stage-13`; in 13b, pairing wired into hosts (`kEnroll`, `rhp-cli pair`) and `rhp-cli --sign-cmd` are open. 13c (production delivery) is planned. ARCHITECTURE §39 (AL1–AL16).

RHP is a remote-code endpoint by design, and it is now used in four very different places: on one developer PC, against a test phone on the LAN, on internal / QA builds, and in store apps on end users' phones driven from an operator's VPS. One security posture can't fit all four: the developer wants no friction, the store app wants nothing an attacker (or the phone's owner) can turn on. Five research passes (a code audit, deployment to phones, secure update prior art, channel and authentication cryptography, the Lua sandbox and dev tooling) found confirmed bugs and structural gaps; the questionnaire of 2026-10-27 decided what to do about them. The research notes are summarized in the PR descriptions.

Threat model (decided): remote attackers (LAN, internet), stolen operator keys, malicious script authors, **and** the device owner (detect and, where the platform allows, resist tampering with the clock, the store and rollback).

## Decisions

### 13a: hardening, sandbox, network, dev

- **AL1 — three hardening levels, a build ceiling that runtime can only tighten.** `RHP_HARDENING=dev|lan|production` (CMake, default `dev` = everything, today's behavior) is written into `<rhp/build_config.hpp>` and read as `Rhp::kBuildHardening`. `config<>::hardening<Rhp::hardening::kLan>` and `host_options::hardening` may only raise it; the effective level is the strictest of the three (a config below the build's level fails to compile). What a production build doesn't allow isn't in the binary (`if constexpr` on the build level), so tampered config, intents or memory patches can't turn it back on. The name avoids `RHP_PROFILE`, which is Stage 11's profiler.
- **AL2 — what each level allows.**

  | | dev | lan | production |
  |---|---|---|---|
  | admin full standard library (io, os, package, debug) | yes | compiled out (admin = patch libraries + admin ops) | compiled out |
  | unsigned observe code | yes | yes (observe limits forced) | compiled out |
  | remote debugger (`kDebug`) | yes | yes | compiled out |
  | `insecure_lan`, `signer<unsigned_scripts>` | yes | refused | refused / compiled out |
  | dev session (auto identity, connect file) | loopback / IPC only | refused | compiled out |
  | observe limits | as configured | capped (AL4) | capped |
  | limits for patch / admin | as configured | as configured | capped (AL4) |
  | mDNS advertise, HTTP gateway | yes | yes | advertise refused; gateway only with `http_require_binding` |
  | release channels (`release::manager`) | as configured | admin channels get patch libraries | also capped (AL4) |

  Release channels run at `manager_options::hardening` (the build's level at least); `host.serve` raises it to the host's level (`manager::harden`), moving running channels into sandboxes made at that level.
- **AL3 — the sandbox bounds what untrusted code can do.** Measured gaps closed for every level:
  - `__gc` finalizers run with Lua's hooks off (no instruction, wall or cancel check), so a script could hang the pump thread forever. Non-admin scripts get a `setmetatable` that refuses a metatable with a `__gc` field (as Luau does); `<close>` variables still work and stay limited.
  - Pattern matching and plain find run in C, where no hook fires: `lstrlib.c` is patched at configure time (exact-match sites, like `lvm.c`) so the matcher and `lmemfind` charge the run's budget and honor cancels and deadlines every few thousand steps.
  - Observe identities can't register lasting handlers (`rhp.after`, `every`, `every_frame(s)`, `on`, `spawn`): those are mutations of the host's schedule.
  - `tostring` / `%p` show an identity-keyed hash instead of a C address (no address-space layout leak to unsigned code).
  - Changes to the shared library tables (`string`, `table`, `math`, `utf8`, `coroutine`, `os`, `rhp`) and the string metatable are undone with the identity: the sandbox snapshots them when it is made and restores them when the identity reverts (`revert_all`), and when a host releases an identity at its last session's end while keeping modules an admin pinned (the rest is reverted, the builtins restored: a pinned module must not rely on builtins it or others changed), so a disconnect leaves no changed builtins behind. (A read-only proxy would add a lookup to every `string.x` and method call on strings.)
- **AL4 — limits per role, and rate limits.** Observe identities get their own limits (`host_options::observe_limits`, default the config's limits). From `lan` up, observe limits are capped by `Rhp::kObserveCaps` (and `cancel_checks = kEverything`); in `production` every role is capped by `Rhp::kProductionCaps`. A cap replaces 0 (unlimited) and any larger value; both cap `cancel_check_instructions` at 10'000 (its 0 means the default 1'000, so the cap bounds what a value comes to). New `limits` fields, per identity: `request_rate` (requests per second, token bucket), `pump_requests` (requests started per `pump()`, served round-robin across identities), `handlers` (timers, frame callbacks, subscriptions and tasks alive at once). 0 keeps today's unlimited behavior in `dev`.
- **AL5 — admission control and transport fixes.**
  - Handshakes: a per-source cap (`limits.handshakes_per_source`, IPv4 address or IPv6 /64), a first-byte deadline (`limits.first_byte_ms`) separate from the handshake deadline, the oldest pending connection evicted instead of a new one refused (a silent one first, else one still unauthenticated after a quarter of the handshake deadline: a handshake under way keeps its slot), so resumes are never blocked behind stalled handshakes. `auth_failed` names the key that was tried.
  - Reliable UDP: a stateless cookie (a keyed MAC over the source address, port and a time bucket) is echoed before any peer state or handshake slot exists, so spoofed Hellos cost nothing (rudp packet revision, not the wire protocol).
  - A reverse-mode (listening) client authenticates candidates before one becomes its session, so an unauthenticated connection can't hold the slot.
  - `insecure_lan` accepts only private, link-local and loopback peers (RFC 1918, RFC 4193, link-local, CGNAT excluded); TLS is the only way past that.
  - A `server_name` is an IP address only if it parses as one (names such as `cafe1` and `db1.de` were treated as addresses and skipped the hostname check); a CA-checked dial to an IP address checks the certificate's IP addresses (both backends); the Python client checks host names.
- **AL6 — a hard kill switch.** `host.set_enabled(false)` refuses connections, closes every session (identities revert as on disconnect; pinned modules stay), stops reverse dialing and stops running scripts: `pump()` runs no requests, handlers, tasks or release channels until it is enabled again. The signed, persisted remote disable is 13c (AL15).
- **AL7 — dev sessions without key files.** In a `dev` build, a host listening only on loopback or local IPC can open a dev session (`host_options::dev_session`): it generates an identity and a signing key for this run, trusts that signer, and writes a connect file (endpoint, identity, signing key) owner-only into the user's config directory (`<config>/rhp/dev/<app>.rhpdev`), removed at shutdown. `rhp-cli connect --dev [app]` reads it. The same wire protocol (the PSK handshake and signatures still run); a non-loopback endpoint refuses the dev session (an HTTP gateway's too: it accepts the same identities), and any process of the same user can read the file (decided: acceptable on a dev machine). Phone pairing (QR one-time secret, a 6-digit CPace code, trust on first use, `adb forward`) is 13b, because it enrolls a device key (AL10).
- **AL8 — key files are owner-only on every OS.** Identity files are created atomically and owner-only: POSIX `O_CREAT|O_EXCL` 0600 then rename, Windows an explicit DACL for the current user (inheritance off). `std::filesystem::permissions` only toggles the read-only attribute on Windows. Loading warns when a key file is readable by others. `rhp-cli keygen` and the Python client default to the patch role (admin must be asked for), never print the PSK unless asked, and the Python client writes 0600.
- **AL9 — release state can't be fast-forwarded.** A revocation list's seq and every floor it raises may move at most `max_seq_jump` past what the host has seen, and a channel's first release is capped the same way (from the host's clock-based ceiling when it has seen nothing), so one stolen `*` key can no longer set seq or floors near 2^63 and lock out every later list. Recovery from a compromised key over the air is the root of trust (AL12).

### 13b: identities and trust (wire revision 7)

- **AL10 — device keys, hosts store only public keys.** A new authenticator: each side holds a key pair, the host an allow-list of client public keys and roles, the client the host keys it pinned (pairing or trust on first use). Both sign the handshake transcript bound to the TLS exporter (TLS required: it is certificate-free already). Ed25519 in software, ECDSA P-256 through a sign callback for hardware keys (Secure Enclave, StrongBox, TPM: the private key never enters RHP), behind a `key_store` interface with file, DPAPI and Apple Keychain built-ins and an app callback (Android Keystore). PSK identities stay for dev and LAN. Pairing: QR with a full-entropy one-time secret and on-device approval, a 6-digit code over CPace (X25519 in Monocypher, checked against the draft's vectors), trust on first use with a prompt, and `adb forward` documented.
- **AL11 — operator certificates and script claims.** Hosts trust an offline operator CA; operators carry short-lived certificates (principal, public key, validity, max role, apps, environments, capability scopes, serial; unknown critical options refuse the certificate). Every script signature carries claims (expiry, app, environment, audience, nonce) under a new signature domain, so a signed script can't be replayed elsewhere or later. Keys and certificates are tagged `env=dev|prod`; production-hardened hosts refuse dev keys. Key custody: split connection and signing files, optional passphrase encryption (Argon2 + XChaCha20-Poly1305), `rhp-cli --sign-cmd` for external signers (YubiKey, KMS, Vault), OS key stores.
- **AL12 — a root of trust.** A versioned root document, signed by an offline threshold, lists the release, revocation and operator-CA keys with roles, thresholds and expiry. Version N+1 needs thresholds of both N and N+1; keys marked compromised drop what they signed (TUF's recover step), retired keys keep it. Revocation lists also cover operator certificates (by serial), signers and device keys.
- **AL13 — capability scopes.** `lib:`, `cap:`, `patch:`, `event:` and `op:` patterns (deny wins) granted per identity (keyring column) and per operator certificate; bindings tag capabilities with `Rhp::cap<"economy.write">`. Checked when a lib is installed, a patch attached, an event subscribed and a request dispatched; a call costs one mask test.

#### 13b formats (specified before the build; *as built* notes say where it differs)

Every signed object below is canonical MessagePack (fixed key order, the same encoder the release manifest uses) signed over `domain || body`; domains are new, so no signature means anything else. Algorithms are named (`"ed25519"`, `"p256"`, ECDSA with SHA-256, raw r||s); P-256 verification uses the TLS backend's crypto and reports `kDisabled` in builds without one.

- **Key handles** (`security/key_handle.hpp`): `key_handle { alg(); public_key(); sign(bytes) -> result<signature> }`, type-erased; built-ins: software Ed25519 (from a seed), and an app callback (hardware keys). `key_store { load(name) -> result<key_handle>; store(name, ...) }`: `file_key_store` (owner-only files, optional passphrase: Argon2i + XChaCha20-Poly1305, Monocypher), `dpapi_key_store` (Windows), `keychain_key_store` (Apple), app callbacks. OS code in `platform/`.
- **Key files are split and tagged.** A connection identity (`name`, `psk` or device key) and a signing key are separate files; each key line may carry `env=dev|prod`. `identity_file` still reads the combined format (old files keep working).
- **Device-key handshake** (`security::device_keys`, a `config<>::auth<>` policy; credential `device_credential`). TLS is required: a handshake whose channel binding is empty fails with `kAuth` ("device keys need TLS"). T = length-prefixed (client alg, client public key, Nc, Nh, host alg, host public key, binding).
  - hello `{scheme = "device", alg, pub, nonce}` (32-byte nonce);
  - challenge `{nonce, alg, pub, sig = sign(host key, "rhp/device/host\0" || T)}`; an unlisted client key still gets a challenge and fails at verify;
  - the client checks the host key against its pins (`known_hosts`: name, endpoint, alg, public key; unpinned: refuse, or ask a trust-on-first-use callback), then answers `{sig = sign(client key, "rhp/device/client\0" || T)}`;
  - frame keys: keyed BLAKE2b with the binding as key over `"rhp/c2h"` / `"rhp/h2c"` || T.
  - Host allow-list file: `name role alg base64-public-key [scopes] [env=dev|prod]`.
  - *As built:* the T fields are each prefixed with their u32 little-endian length (algorithms as their names, "ed25519" / "p256"). `device_keys{device_allow_list, key_handle host_key, shared_ptr<const revoked_identities>}`: revocation is the app handing in `release::manager::identities()` (or its own set), asked at every handshake; a revoked or unlisted key is challenged like a listed one and fails at verify. `known_hosts` lines are `endpoint alg base64-public-key` (no name column: the endpoint is the name the client dialed), copies share their entries, a file-backed set rewrites its file owner-only on every pin; a changed key is refused without asking. The trust-on-first-use callback runs inside the handshake, after the host's signature checked out; `rhp-cli` refuses, asks y/n on a terminal and connects again with only that fingerprint accepted (`--trust-new-host` without a terminal; `--known-hosts`, default `<config>/rhp/known_hosts`). The welcome's `host_key` is the host key's fingerprint (`key_fingerprint`), left out without one; a client whose handshake proved another key refuses the welcome. The Python client stays PSK-only for now (its TLS extra, pyOpenSSL, isn't installed where this was built, so the path couldn't be run).
  - *As built (AL11, env tags):* at effective production hardening `Rhp::host` copies its authenticator and its trusted signers without the entries tagged `env=dev` (`keyring::without`, `device_allow_list::without`, `trusted_signers::without`, found with `requires`): one check per kind, in the host's constructor. A dev PSK or device key then fails its handshake with `kAuth`; a dev signer's scripts are unsigned to that host (`kBadSignature`). Untagged keys stay.
- **Operator certificates** (domain `"rhp/opcert\0"`): `{serial, principal, alg, pub, not_before, not_after, max_role, apps, envs, scopes, critical}` signed by an operator CA (Ed25519). Unknown `critical` entries refuse the certificate.
  - *As built:* `alg` is `ed25519` or `p256` (65-byte SEC1 key): `certified::key` signs through a `key_handle` (software or a hardware callback) and the trust checks with `security::verify`; P-256 needs the TLS backend (`kDisabled` without one). `rhp-cli cert issue --device` certifies an identity's device key. Each `scopes` entry is one pattern, checked when issued. With a served `release::manager`, the root's `operator_ca` role (Ed25519 keys) replaces the trust's own CAs while it names any (a root naming none leaves them), rotating with the root without a restart, and the manager's identity revocations withdraw serials (decimal text): `certified::trust::set_root_of_trust`, separate from the app's `set_revocation_check`.
- **Certified script signatures** (signer policy `security::certified`, domain `"rhp/script-claims\0"`): the value is `{cert, claims, sig}`, claims `{not_after, app, env, audience, nonce, identity}`; the host checks the chain to a trusted CA, validity, the claims against its context (identity name, role, app, env, host id; `audience` empty = any), the certificate's `max_role` and scopes, and the revocation lists. The signer concept gains an optional context-taking `verify` (checked with `requires`, so existing signers are unchanged).
- **Root of trust** (domain `"rhp/root\0"`): `{version, expires, keys: {id: {alg, pub}}, roles: {root, release, revocation, operator_ca}: {keys, threshold}, compromised: [ids]}`. Version N+1 must carry thresholds of N's root keys and of its own; stored on the host next to release state. Release trust and the operator CAs come from it when one is configured; `compromised` keys' stored lists are dropped on restore.
  - *As built:* keys are `{alg, pub, channels}` (`channels` limit a release key, like `trust` patterns; empty = every channel). The app supplies the anchor (`manager{signed_root, ...}`), which needs only its own root threshold; versions walked to are stored as `trust/root/<version>` and walked again on restore. Expiry: an expired root is refused as an *update* (the newest of a walk, with `clock_skew`), but the root a host holds stays in force after it expires, so a late operator can't lock devices out (TUF would refuse to act; a freeze is 13c's signed index, AL14). Retired keys (no longer in any role) keep what they signed: stored releases also verify against earlier roots' release roles less compromised keys. The recover step drops revocation and identity lists signed only by compromised keys and takes back what they raised; a floor only compromised material raised comes down to the highest seq a trusted key shipped in that channel (`trust/seen`) or the remaining lists' floor, so older releases can't be replayed below it. The root lives in `release` (its encoder, signature lists and store), not `security`.
- **Identity revocations** (domain `"rhp/identity-revocations\0"`, envelope `rhp = "identity-revocations"`, signed by the root's revocation role): `{seq, issued_at, cert_serials, signer_keys, device_keys}`, cumulative and seq-capped like AL9. Release revocation lists keep their format (stored lists stay readable).
  - *As built:* serials are strings (a numeric serial is its decimal text); keys are `{alg, pub}`. Without a root the manager's `"*"` release keys sign them. `release::manager::identities()` is a thread-safe `security::revoked_identities` (`is_revoked_serial`, `is_revoked_signer`, `is_revoked_device`) for the certificate and device-key checks; `host.serve` refuses scripts whose signer key it names (`kRevoked`, found through the trust policy's `find(name)`).
- **Capability scopes**: patterns `lib:<name>`, `cap:<name>`, `patch:<id>`, `event:<name>`, `op:<op>` with `*` / `prefix.*`, `!` denies, deny wins, no column = `*`. Bindings: `Rhp::cap<"economy.write">`.
  - *As built (certificate scopes):* the trust hands a verified certificate's scopes to the host (`signature_context::scopes`); the host refuses an op they don't allow and runs the exec / load / reload under the identity's scopes met with the certificate's (`scope_set::intersect`) through `sandbox::narrow`. The narrowing is per request (exec) or per module revision (load / reload), follows the running code's owner, and widens `context::denied_caps_` while it runs, so a capped call still costs one mask test. Handlers: a narrowed module's timers, event and patch handlers, tasks and later calls keep its narrowing (they carry its owner); a narrowed exec may not register any (the identity's scratch module is shared, so they would outlive it). A rollback runs as the revision it returns to was narrowed. Libs are installed per identity, so a certificate that denies a lib or sub-lib the identity has is refused rather than hiding it for one script. Unsigned ops (call, unload, ...) are the identity's alone.
- **Pairing** (*not built yet*: the primitives are, `security/pairing.hpp` (links, the one-time secret book, six-digit codes) and `security/pairing_cpace.hpp` (CPace over X25519, draft-21 vectors); the host side, `kEnroll` and `rhp-cli pair` are open): a host in pairing mode accepts a one-time pairing credential (QR: `rhp-pair://host:port?secret=<base64url 32 bytes>&fp=<host key fingerprint>`; CPace over a 6-digit code; or an unknown device key with on-device approval) whose session may only send `kEnroll {name, alg, pub}`; the app approves through a callback and persists the allow-list. `rhp-cli pair` shows or reads the QR / code. `adb forward` / `adb reverse` documented for USB.
- **Wire revision 7**: new ops `kEnroll` (pairing), `kTrust` (push a root document or identity revocations; observe, since they carry their own signatures, like `kRevoke`); the welcome carries the host's device-key fingerprint when it has one. Hosts, clients, rhp-cli, the Python client and the VS Code extension move together.
  - *As built:* `kTrust` is op 44; `release_status` also reports `root_version` and `identity_seq`. `kEnroll` isn't in the op list yet (pairing isn't wired); it will take the next free number without changing the revision's other ops.

### 13c: production delivery

- **AL14 — releases are the production path, support sessions are opt-in.** Phones pull signed release and revocation files over HTTPS with the OS network stack and hand the bytes to RHP; a signed, short-expiry channel index defeats freeze attacks (`max_staleness`). Release state is MAC'd with a platform-keystore key and can use an app-provided monotonic counter. Live sessions on store builds are support sessions: started by the user, in the foreground, time-limited, reverted at the end, through `Tools/rhp-relay` (phones and operators both dial it over `wss://` on 443; it splices streams and sees only RHP's end-to-end TLS). A `mobile` limits preset and `host.pause_network()` / `resume_network()` fit iOS and Android background rules.
- **AL15 — operations.** Hash-chained audit (sequence, previous hash, signed checkpoints, host id, app and build on every event), forwarded to operators over the session and to an app collector hook; attestation hooks (Play Integrity, Android Key Attestation, App Attest) bound to the transcript and exporter, verified by the app or VPS; a signed, persisted remote disable; hybrid ML-KEM where OpenSSL 3.5+ is used; Mbed TLS stays at 4.2 with a recorded fallback plan.
- **AL16 — store tiers.** dev (everything), store (production hardening: releases and support sessions), off (`RHP_ENABLE=OFF`). Store builds must disclose remote updates (App Store 2.5.2 / 2.5.19, DPLA 3.3.1(B); Play Device and Network Abuse, Malware, Deceptive Behavior); the guide carries the review-notes and consent pattern.

## Alternatives

- **Runtime-only profiles:** a production binary would still contain every dev feature, one config change away.
- **No authentication on loopback in dev:** any local process, or a browser through DNS rebinding, could run code (the Node `--inspect` and Chrome remote-debugging incidents).
- **A Noise channel for encryption without TLS:** TLS already works without certificates (ephemeral host certificate, RFC 9266 binding); a second channel stack is new cryptography to review and keep in step. Kept TLS-only.
- **Length caps instead of patching `lstrlib.c`:** heuristic; a short pattern can still backtrack for minutes.
- **A finalizer budget instead of refusing `__gc`:** more patching of Lua's collector for a feature scripts rarely need.

## Consequences

`dev` builds behave as before except where a confirmed hole closed for every level: no `__gc` for non-admin scripts, observe can't register handlers, changed builtins are restored on revert, pattern matching is limited, revocation and first releases are capped, key files are owner-only, keygen defaults to patch. 13b changes the wire protocol (revision 7) and the signature format.
