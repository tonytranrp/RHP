# Stage 12: a test engine for Lua scripts

**Status:** implemented (branch `stage-12-lua-test-engine`). ARCHITECTURE §38 (AK1–AK12). Usage: [Testing scripts](../guide/testing-scripts.md).

Until Stage 12, testing the Lua that users write against their own `Rhp::lib` API meant running the program, or writing C++ tests that drive a sandbox by hand. Neither checks what a script costs, and neither is how Lua developers test: they expect busted or Jest. Stage 12 adds `Rhp::test`: Lua test files run offline against the program's real libs (or fakes), with the tools people expect from a modern test runner, plus measurements no Lua runner can make from inside Lua.

## Decisions

- **AK1 — tests run in real sandboxes.** A test file runs in an RHP sandbox with the program's libs installed, the modules of `--scripts` loaded and the framework in the scratch environment (the modules under test don't see it). Bindings, roles, undo, limits and the scheduler are the ones the program has. A separate Lua state with mocked globals would test a different runtime. One sandbox per file by default; `--isolation test` gives each test its own.
- **AK2 — each test is a request between a checkpoint and a revert.** Setup of the enclosing blocks runs first (it lasts for the file), then `checkpoint`, the test as one request (hooks, body, `finally`), measurements, `revert_to`. So everything a test does that RHP journals is undone: lib effects, variable writes, patches, timers, frame callbacks, subscriptions, tasks, swapped members. After the revert the runner compares the sandbox's counts (schedule entries, subscriptions, tasks, waiting requests, ledger effects, variable values) with before the test: anything left is a leak and fails a passing test. Irreversible effects are noted, or fail with `test.expect_undone()` / `--strict-undo`. Globals a test creates are removed and noted. Events still queued when a test ends are delivered before its revert, so they can't reach the next test.
- **AK3 — the clock is fake and the runner drives it.** The sandbox's clock is the runner's. `test.advance` / `test.frames` send a command to the runner and yield (`rhp.sleep` / `rhp.wait`); the runner steps the clock through every due time in order and pumps, so timers fire at their own times. A test that waits on its own (an event, a deferred result) gets pumps, and the clock jumps to the next due time when nothing else can move it. `os.time` / `os.clock` follow the fake clock. A wall-time limit (the test's `--timeout`) stops a test that never yields; `--max-frames` stops one that waits forever on frames; one waiting for an event nothing can fire is reported as such.
- **AK4 — exact instruction counts.** The meter adds the count hook's ticks and, after every resume, the remainder of the countdown Lua keeps per thread (read through Lua's internals in `lua_internals.cpp`, the one file besides the sandbox that knows them), so the count is the number of instructions the VM ran, checked against a plain `lua_State` counting every instruction. Coroutines are credited when they yield (a metered `coroutine.wrap` and guarded `coroutine.resume`). Metering never changes limits or cancels: credits go to the run budgets too. Allocation counters (allocations, frees, bytes, peak, objects by kind from Lua's allocation tags) are always on in the sandbox allocator: an add and a compare per allocation.
- **AK5 — coverage from the compiled code.** Executable lines come from walking each compiled prototype's line information (Lua's own valid-lines logic, reimplemented because the single-file Lua build makes it static), so totals are exact: lines that never ran count as 0. Hits come from the line hook, armed only while coverage (or the debugger) needs line events. Exclusions: `rhp: coverage off/on`, `luacov: disable/enable`.
- **AK6 — the bridge is a scratch-only table.** `__rhp_test` (kinds of values, member lists, journaled swaps of lib members, module exports, handle methods and lib variables, the meter, garbage collection, due times, events and patch points by name, coverage, stack frames, the runner's services) exists only in the scratch environment of a sandbox with `enable_testing`. Swaps go through the ledger as effects, so a checkpoint undoes them like any other effect. The framework is Lua (embedded at build time from `Src/rhp/test/lua/*.lua` by `cmake/RhpEmbed.cmake`); the bridge stays small and C++.
- **AK7 — both test dialects.** busted's DSL with luassert-compatible assertions and matchers (words chain, the last string is the message), and Jest-style `expect` over the same checks. Spies, stubs and mocks follow luassert's names. Deep equality names the first difference by path; failures carry expected / actual for diff views.
- **AK8 — fakes two ways.** `Rhp::test::fake<L>` is a lib with L's names, types, tags and handles whose functions are recorders (compile time, the scripts can't tell). An API description (`sandbox::api`, `rhp.api()`, `--dump-api`, `rhp-cli test --api` / `--api-from`) builds fakes in Lua without the program. Both share `fake.calls` / `fake.returns` / `fake.reset`, are reset for each test and can be strict.
- **AK9 — snapshots, properties and fuzzing in Lua.** Snapshots are readable Lua next to the test file (`__snapshots__/<file>.snap.lua`), `--ci` refuses new ones, `--update-snapshots` rewrites and drops obsolete ones, an unreadable file fails its tests and is never rewritten. Property tests use a seeded splitmix64 generator and greedy shrinking. Fuzzing generates and mutates inputs (coverage-guided when coverage is on) and keeps crashes in `__fuzz__/` as regression inputs.
- **AK10 — reports for people and machines.** Text, TAP 14, JUnit XML, JSON events (one per line, what the VS Code extension reads) and GitHub annotations; LCOV and Cobertura for coverage; folded stacks for profiles. Paths are relative to `--root`.
- **AK11 — entry points.** `Rhp::test::main` makes a program's test executable (its real libs); `rhp-cli test` runs files with the `rhp` API, fakes from a description, or a program's executable (`--exe`, through `platform::run_process`); `rhp_add_lua_tests` (installed with the package) makes each file a ctest test; `clients/vscode` puts tests in VS Code's Test Explorer. With `RHP_ENABLE=OFF` files report that Lua is compiled out while the API description and fakes still work.
- **AK12 — measured and made cheap.** `Tests/bench/bench_testing.cpp` measured the engine before optimizing. The framework is compiled once per process and later sandboxes load its bytecode (`sandbox::exec_cached`, for trusted sources only); one full collection on each side of a measured test; assert and match chains are made once per word sequence; `expect` builds messages only on failure; spies don't copy arguments that hold no tables. Results in [benchmarks](../benchmarks.md#stage-12-test-engine).

## Alternatives

- **busted (or another Lua runner) on stock Lua:** no RHP sandbox, so no real bindings, roles, undo or scheduler; it would test a different runtime and couldn't count instructions or undo C++ effects.
- **Tests in C++ only (Catch2 driving a sandbox):** what RHP's own tests do; it isn't how script authors work, and every assertion would be C++.
- **Mocks by replacing globals:** libs are proxies whose members are resolved through a members table; replacing a global misses code that captured the lib, and nothing would undo it. Journaled swaps reach every caller and are undone by the checkpoint.
- **Sampling the instruction count (the profiler's way):** approximate; budgets and regressions need exact counts.
- **luacov for coverage:** a Lua line hook per line (slower), and only lines that ran are known.

## Consequences

Tests are deterministic: the clock is fake, inputs come from a printed seed, and instruction counts don't vary between runs or machines. Coverage costs about 3x on line-dense code (Lua's line hook); metering costs nothing measurable. Patch points and events are process-wide, so a test executable shares them between files (each test's patches are undone). Not done: parallel test files (one runner, one thread), watch mode outside the editor, mutation testing.
